## AI Layer

So I like the fact that the AI would not actually read the data but would just be creating queries. From that perspective, I wonder if we can build some kind of low-code application for users to query the data themselves without even invoking AI at all. I don't know what would be simpler. Then the other part is, would it still be hostable for free on Cloudflare? Because the more I think about it, say something like, "Hey, tell me all the marketing emails from the last three months that I have not read." Well, how do I trust what you decide as a marketing email? Right. So, it might be better if I could drag and drop and say a time horizon, a label that we've given some emails, and then read, unread, or sitting in inbox versus sitting in archive. And then also have some kind of exclusion where, as I keep reading emails in some kind of a preview, I can keep adding stuff to exclusion to exclude stuff, and it keeps updating. Perhaps we don't need to start coding the AI layer straight away, but this is going to be a big part of the application, so it might be important to keep in mind as we are making architectural decisions right now on different features. I imagine labeling is going to be a big part. In fact, if we go in the direction of low-code, having some kind of reporting on my ingested email is probably important. To show me the number of emails I have from different senders and domains, and having some kind of classification next to them would be a good way for me to get started and start getting value from the product right away. Then also, the actions being taken can be things like delete, archive, as well as creating some kind of rule within my Gmail inbox, so future emails are also impacted. In fact, if we get the AI layer to work, I feel like that should be front and center. And the recommendation thing can be a second screen or be like, hey, okay, show me the recommendations because I don't want to do stuff manually. But really, I want to be in control. Because I personally prefer that, and I am building this product for myself first and foremost, as well as my family. And so the more I think about it, the more I feel like some ready-made scripts or ready-made low-code stuff that I can do on my inbox would be the correct first step. And not straight away starting to invoke some kind of AI to write code for me. Because even if I am invoking the AI and I am not allowing it access to my email contents, it is equally important that the labeling is done correctly. I will need to rely on classification from Gmail as well as some kind of regex or some kind of deterministic predefined criteria to make this determination. The rest will involve manually searching for an email address or domain to create the label myself, as I handle the low-code tasks. And again, the purpose would not be to create the label itself, but if I have a low-code option and some kind of reporting, and I don't agree with the predetermined label, at the very least if I can see it, I can add stuff in exclusion or include stuff.

## Mobile

Something that I have been thinking about a couple of times now, but have not yet added in the plan, is how the experience will be on mobile. All of the UI things that I have been commenting on have been on my laptop because the localhost will only run on my laptop. But I think at some point we also need to consider the mobile use case and how both the UI as well as the user experience will be if someone does this on their cellphone. And so I, and we, haven't really paid attention to it, but I think it might change some things on an architecture basis if we want to be able to do it on the mobile phone. I wonder what all will need to change if it is mobile versus on a laptop, and that might add complexity which we haven't thought about yet.

## Data Security/Privacy

This has to be a key part of the implementation. Data needs to be secure, and the data needs to be private. The application should not store anything. It should auto-expunge data after some time. If the user leaves things midway, we need to auto-expunge, and we should think about other scenarios where we need to auto-expunge. Then there needs to be some kind of master expunge logic where, no matter what's happening, even if the tab stays open or whatever, the data has to get deleted after a certain time and make the user do everything again. Another aspect would be the security aspect of it, right? We will be relying on Cloudflare for some of it, and so that may be something that we think about after we've deployed it but before we advertise it. I think these are some key considerations that we need to keep top of mind. These cannot be a second priority, and these are deal breakers if we cannot figure certain things out. We cannot let a third party get access to someone else's data or our data because this is sensitive stuff.

## 100K Inbox

While both my wife and I have around 50,000 emails total in our inboxes, I can totally foresee that there are people who have double, triple, maybe 10 times that much email in their inboxes. So how do I deal with that? What are the architecture changes needed to make this a reality? Is there a possibility to have it run as an application on someone's computer and using local memory/processing? If it needs to be hosted, what architecture changes are necessary? And obviously, there is the part about Cloudflare. Free deployment will no longer be a possibility, and I'll need to move to some kind of paid tier. But I wonder if there are alternate options, like someone running it locally or being able to use someone's local memory, or doing some kind of architecture changes where I can still keep it free while hosting on an actual Gmail inbox.
