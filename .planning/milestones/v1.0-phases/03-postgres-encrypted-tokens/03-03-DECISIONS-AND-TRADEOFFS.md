## D-3.1  Flyway V1 SQL strategy: Two dialect files, not placeholders / conditional SQL

### Alternatives rejected
1. **Flyway placeholders with `${timestamp_type}` swap.** Would have kept one file with `${blob_type}` / `${json_type}` / `${timestamp_type}` variables, switched via `spring.flyway.placeholders.*=...` per environment.
   - Why rejected: (a) Flyway placeholders do NOT substitute inside enum string literals inside `CREATE TYPE`/`CHECK` clauses reliably. (b) Adds a "gotta pass the right placeholder values" step to `java -jar` invocation for every single local run. Footgun for anyone bringing up the app cold.
2. **Hibernate `ddl-auto=update` in dev, Flyway only in prod.**
   - Why rejected: (a) PITFALLS J1: "Schema management must be deterministic — ddl-auto in any non-NONE mode on production is a fail." (b) If `update` is used at any point, you lose the guarantee that what you tested locally is what you run in prod.
3. **Single universal SQL file with plain ANSI types only.** Use `TIMESTAMP` / `BLOB(2G)` / `CLOB` / `VARCHAR(255) ARRAY`.
   - Why rejected: (a) PG's `JSONB` is the whole reason we picked Postgres — it has GIN indexes on JSON fields. Using a universal `TEXT` or `JSON` (not JSONB) means losing the most important Postgres feature in Phase 7 (we'll want to index `inverse_action_data` to speed up undo lookups for large accounts). (b) PG's `BYTEA` (BYT-E-Array) is not LOB; Hibernate's native mapping for `@Lob byte[]` on PG has historically been OID-by-reference with separate large-object storage, creating vacuum pain. `BYTEA` is materially different from `BLOB` and we want BYTEA in prod specifically to avoid the large-object table in Postgres.

### Decision: Main + test-scope override (what we actually did)

- `src/main/resources/db/migration/V1__create_schema.sql` → strictly PostgreSQL 16+ native types. Uses BYTEA, JSONB, TIMESTAMPTZ, TEXT[], bigserial, `now()`.
- `src/test/resources/db/test-migration/V1__create_schema.sql` → strictly H2 2.3+ types. Uses BINARY LARGE OBJECT, JSON, TIMESTAMP(6) WITH TIME ZONE, VARCHAR ARRAY, GENERATED BY DEFAULT AS IDENTITY, CURRENT_TIMESTAMP.
- `spring.flyway.locations` **defaults to** `classpath:db/migration` in application.properties (prod).
- Tests override to `classpath:db/test-migration` via `@TestPropertySource`. Test classpath root has only the H2 copy. Main classpath root has only the PG copy. No collision, no shared migration version numbers.

Trade-off:
- (+) Prod gets full Postgres-native features (JSONB GIN indexable, BYTEA no LOB table, TIMESTAMPTZ tz-aware).
- (+) Tests are zero-Docker, run anywhere Travis runs mvn test, finish in ~3s.
- (+) Migration ID "1" is still unique in each classpath; no "multiple migrations same version" Flyway error.
- (-) **Schema drift risk between the two V1 files.** Mitigation: (a) Hibernate `spring.jpa.hibernate.ddl-auto=validate` runs in BOTH tests and prod. Validator compares entity model → live DB schema. If anyone edits main V1 without editing test V1, tests fail INSTANTLY. (b) The entity fields are the *canonical* schema contract; the two SQL files are just two dialect serializations. If field renames happen, entity change is the single source and validator catches mismatches.
- (-) User reading migration has to do a "find" to see which V1 file applies to which env. Mitigated with huge block comment at the top of test V1 explaining it's a test override only.

## D-3.2  `(provider, providerAccountId)` as the OAuth persistence key, NOT email

### The bug this prevents
On Google OIDC, the email claim in `id_token` is `user@gmail.com`. But Gmail's actual OAuth `sub` claim (Google's account UID) is a 21-digit numeric string. If a user later changes their Gmail primary alias via Google Account settings → their email claim changes, their OAuth `sub` does NOT. If we keyed by `email+provider`, the lookup on the NEXT login would MISS, and we'd either:
1. Duplicate the row (email changed → inserted as new user → sender_stats split across two accounts), OR
2. Throw a unique-constraint violation for `provider_account_id` (if we still had the separate unique constraint).

For Microsoft accounts, the equivalent issue is: changing UPN in Azure AD / Outlook aliases.

This is the exact bug pattern that killed many open-source "Sign in with Google" apps in 2023–2024 when people migrated to @googlemail → @gmail aliases or vice versa.

### Decision
Per `JpaOAuth2AuthorizedClientService`:
- `loadAuthorizedClient(clientRegistrationId, principalName)` → `findByProviderAndProviderAccountId(regId, principalName)`.
- `saveAuthorizedClient(client, authentication)` → upsert by `(provider, principalName)`.
- `removeAuthorizedClient` → same tuple.
- Email is stored purely for user-visible display + logout cascade convenience. The unique constraint on `(email, provider)` still exists, but is now a **secondary integrity check**, not the lookup key.

Trade-off:
- (+) Correct OAuth2 semantics per RFC 7591: OAuth client implementations MUST use the `sub` / OIDC subject as the stable user identifier, never the email.
- (+) Compatible with Phase 8's eventual identity linking if we ever want to do "merge my Gmail and Outlook inboxes" (two rows, same user — out of scope for MVP but the key structure doesn't preclude it).
- (-) `CascadeDeleteLogoutSuccessHandler` still uses email+provider for the delete because that's what OIDC principal `getAttribute("email")` returns directly, and we have the unique constraint ensuring that tuple matches exactly one row even under future alias changes. Means two paths. Mitigation: repository exposes both delete variants; both paths return 1 row when correct.

## D-3.3  AES-256-GCM blob format = `IV (12) || CIPHER || TAG (16)` (concatenated)

### Alternatives rejected
1. **Two-column layout: `encrypted_access_token_iv BYTEA, encrypted_access_token_cipher BYTEA, encrypted_access_token_tag BYTEA`.**
   - Why rejected: 6 columns of noise instead of 2. Every read/write needs to set/fetch 3 fields. Spring's `OAuth2AuthorizedClientService` API returns a single `OAuth2AccessToken.getTokenValue()` String; we only ever store one opaque value per access token anyway.
2. **Bouncy Castle `AES/GCM-SIV` (nonce-misuse resistant).**
   - Why rejected: (a) Adds BouncyCastle provider dependency (~6 MB, another native library conflict risk in GraalVM-aware Boot). (b) GCM-SIV is ~3× slower on typical JVMs. (c) We already randomise IV per encrypt via `SecureRandom.nextBytes(12)` (see CryptoUtil line 28), so nonce-misuse is not a plausible attack surface.
3. **ASN.1 / DER / TLV-wrapped blob.**
   - Why rejected: (a) Adds a library (BouncyCastle ASN.1). (b) Debug experience is terrible. The "read the first 12 bytes" format is trivially introspectable with any hex dumper, python3 struct, or even a unit test comparing array slice lengths.
4. **Store the version byte first (0x01 || IV || cipher || tag) to allow future algorithm migration.**
   - Why rejected: We already HAVE `aes_key_id TEXT DEFAULT 'v1'` on the `user_accounts` row, which covers "algorithm upgrade" AND "key rotation" cases simultaneously. If we ever move to AES-GCM-SIV or ChaCha20-Poly1305, we introduce a new aes_key_id like `aesgcm2-siv-v1`, and a rekey routine reads by key_id, decrypts with old, encrypts with new, updates key_id. A version byte inside the blob would be redundant with the column.

### Decision: Concatenated `IV ‖ ciphertext+tag` in one BYTEA column

The Java Cipher `AES/GCM/NoPadding` **outputs ciphertext+tag concatenated by default** in `doFinal()` — that's a Java standard. We only *prepend* the 12-byte IV ourselves. Decrypt reads first 12 bytes → IV, remaining bytes → passed directly to `cipher.doFinal()` → which internally splits out the last 16 bytes as auth tag.

Trade-off:
- (+) Single binary blob to read/write. Clean Hibernate mapping.
- (+) Fail-fast on truncated data: any blob shorter than 12+16=28 bytes is immediately rejected with IllegalArgumentException in decrypt. (Encrypted access tokens are always longer: JWT alone is ~1KB.)
- (+) Zero extra columns, zero extra libraries.
- (-) Cannot index by IV or tag. Not an issue — this data is opaque to SQL queries.

## D-3.4  `CryptoStartupValidator` hard-fails if `AES_256_KEY` is missing or weak

### The alternative (lazy first-encrypt fails)
Without a validator, the app would boot happily, user OAuths in, and then `JpaOAuth2AuthorizedClientService.save()` → `CryptoUtil.encrypt()` → boom, `NullPointerException` or "key not initialized" in the middle of a login. That's a terrible first-run experience.

Worse, in Spring Boot's default error handling, the uncaught CryptoException would bubble up as an HTTP 500 to Google/Microsoft's OAuth callback — the user would see a generic "redirect URI error" and never diagnose that the actual problem was a missing env variable.

### Decision: `ApplicationRunner @Order(Ordered.HIGHEST_PRECEDENCE)`

Validator runs *after* all beans are wired (so we know CryptoProperties @Value resolution worked), *before* any HTTP endpoint is served, *before* any ApplicationListener fires for OAuth login success events. Throws an IllegalStateException with an exact copy-pasteable python3 one-liner for key generation.

Trade-off:
- (+) No way to bring up the app unprotected.
- (+) One-line message tells the user exactly what to do — no stack trace hunting needed.
- (-) Breaks the "run on empty .env first-thing" happy path. Mitigation: Phase 2's old scenario (`mvn spring-boot:run` without any env vars) is no longer possible. This is intentional because there's no secure way to handle missing encryption gracefully. Future users are expected to either: (a) set AES_256_KEY in `.env` before first boot; or (b) rely on future docs/error message telling them to run `python3 -c ...` — error message is explicit enough.
- (-) Ordered.HIGHEST_PRECEDENCE doesn't actually guarantee "FIRST before any other runner" if another library also claims HIGHEST_PRECEDENCE; Spring uses insertion order then. We're OK because we own all ApplicationRunners for now (only this one + maybe Phase 8 scheduled warmups). If it ever matters, we'll introduce an order-bias layer.

## D-3.5  `@Lob byte[]` for encrypted tokens (not `@JdbcTypeCode(SqlTypes.VARBINARY)`)

### The bug this fixed: B14
H2's SchemaValidator threw `found [BLOB], expecting [VARBINARY(255)]` when entities used plain `byte[]`. On Postgres, plain `byte[]` maps to VARBINARY-equivalent `BYTEA` which is fine, but H2's type system distinguishes `BINARY LARGE OBJECT` (what we declared in SQL) from `VARBINARY`.

### Decision: `@Lob` annotation on the two encrypted token fields
Hibernate mapping after `@Lob`:
- **PostgreSQLDialect**: `@Lob byte[]` → `Types.BLOB` → Postgres JDBC driver reads/writes as `BYTEA` via setBytes on the underlying Blob proxy. The table column is still `BYTEA` (Postgres does not force OID LOB unless you use `@Lob + @Column(columnDefinition = "oid")`, which we didn't).
- **H2Dialect**: `@Lob byte[]` → `Types.BLOB` → maps directly to our `BINARY LARGE OBJECT` column declaration.

Both dialects now pass validate, with no extra JdbcTypeCode annotation needed beyond `@Lob`.

Trade-off:
- (+) One annotation, both dialects happy.
- (+) Also future-proofs the column length. VARBINARY(255) would have truncated encrypted tokens at 255 bytes, which would work for a short JWT (~1.5 KB) but fail silently with Hibernate's default `batchUpdate` truncation. `@Lob` lifts any size limit completely.
- (-) On older Postgres JDBC drivers (pre-42.2.x) `@Lob byte[]` actually created separate `pg_largeobject` entries. Risk accepted: our pinned version (from Spring Boot 3.5.x managed dependencies) is pg-jdbc 42.7.x which does NOT create pg_largeobject for BYTEA-backed @Lob. Confirmed implicitly by our V1 schema using BYTEA — if it were using pg_largeobject, validator would mismatch because the column wouldn't be BYTEA.

## D-3.6  ON DELETE CASCADE at DDL level, NOT `@OneToMany(cascade = REMOVE)` at JPA level

### Why JPA cascades would be wrong here
The three child-tables are NOT fetched as `@OneToMany` collections on the entity. We deliberately chose *not* to map them as JPA relations:
- Fetching 50,000 `SenderStat` rows and 20,000 `UserAction` rows whenever we load a `UserAccount` is a performance disaster.
- `JpaOAuth2AuthorizedClientService` only ever needs `UserAccount` fields for token encryption/decryption.
- Hibernate's default for `@OneToMany` is LAZY, which is fine — but then `CascadeType.REMOVE` is silently **skipped** when running `@Modifying deleteByEmailAndProviderIgnoreCase(...)` derived-delete queries, because those don't load the entity into the PersistenceContext at all. That means cascade would only fire when calling `repository.delete(accountEntity)`, NOT on bulk delete queries. This is an extremely common gotcha in Spring Data JPA apps.

### Decision: FK constraint at DDL level
```sql
account_id BIGINT NOT NULL REFERENCES user_accounts(id) ON DELETE CASCADE
```

Postgres (and H2) then delete the child rows directly inside the database engine. No need for JPA-side cascade. Works for every delete path:
- `repository.delete(account)` (entity)
- `repository.deleteById(id)`
- `repository.deleteByEmailAndProviderIgnoreCase(email, provider)` (derived, BULK)
- Manual SQL: `DELETE FROM user_accounts WHERE id = 42;`
- psql command-line: user runs a DBA cleanup command (our Phase 8 orphan session cron will do this via JDBC template).

Trade-off:
- (+) Works for ALL delete paths, not just JPA entity-delete.
- (+) 1 round trip to DB instead of fetch all children IDs + delete each.
- (-) ORM-agnostic: if we ever swap DBs (MySQL), `ON DELETE CASCADE` syntax differs slightly. Mitigation: we're explicitly locked to Postgres per Project.md §3 "DB: Postgres".
- (-) Harder to see the behaviour just by reading the entity classes. Mitigation: big Javadoc comment on `UserAccountRepository.deleteBy*` methods referencing the DB-level cascade.

## D-3.7  Test scoped Flyway in `src/test/resources/db/test-migration/`, NOT `src/main/resources/db/migration` with `spring.flyway.encoding` hacks

Alternative considered but rejected:
- Use `src/main/resources/db/migration-h2/V1__create_schema.sql` with `spring.flyway.locations = classpath:db/migration-h2` for tests.
- Problem: anyone later adding `V2__add_something.sql` would need to put it in TWO places, every single time. If they forget the h2 copy, tests keep using V1 while prod advances to V2 — validator drifts silently until someone runs `mvn test` months later and hits a bewildering entity mismatch.

Decision:
- Migration files live in exactly one production-classpath location. For each dialect override, ONLY the currently-highest version gets a test override.
- Rule of thumb: if V2 doesn't use any PG-only types, we don't create a test override for V2, we let Flyway run the native main copy against H2 (H2 is fine for most DDL like `ALTER TABLE ADD COLUMN`, new indexes, etc.)
- Future migration authors should ask themselves: "Does this Vn use a PG-only shorthand (TIMESTAMPTZ, JSONB cast syntax, CIDR, ARRAY append operators, CREATE EXTENSION)?" If yes → add test-scoped override under `db/test-migration/Vn__<same_description>.sql`. If no → skip.

## D-3.9  Docker Postgres version pinned to `postgres:16-alpine` (NOT `postgres:17`)

Reasoning:
1. PostgreSQL 16 is the latest *stable* release with 12+ months of production mileage; Flyway 11.x, Postgres JDBC 42.7.x, and Hibernate 6.5.x are all explicitly validated against PG 16.
2. PG 17 changed some JSONB storage internals (TOAST strategy tweaks) and the exact on-disk JSONB representation is not our concern, but we want to avoid first-adopter incompatibilities.
3. Alpine image is ~80 MB vs Debian's ~250 MB. Colima / Docker pull time matters for daily local dev loop.

Trade-off:
- (+) Faster pulls, less RAM, validated dependency matrix.
- (-) PG 17 MERGE command (SQL-standard) & pg_stat_io improvements unavailable. Acceptable for MVP. Phase 8 can upgrade when Cloudflare-supported Neon PG versions finalise their default.
