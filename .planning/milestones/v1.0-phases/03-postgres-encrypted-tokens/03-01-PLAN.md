# Phase 3 — Postgres + JPA Entities + AES-256-GCM Encrypted Refresh Token Store

**Rationale:** "Without a persistence layer, refresh tokens evaporate on JVM restart, sign-out has nothing to cascade-delete, and Phase 4/5 can't cache sender stats or write the undo log."
**Effort:** Medium
**Dependencies:** Phase 2 complete (login works; OAuth2AuthorizedClientService bean currently in-memory and easily swappable).
**Critical path:** Must be done before Phase 4 (Gmail API client needs stored encrypted refresh tokens → Gmail client constructor pattern uses Spring Data repo to load credentials per user). Must be done before Phase 6 (sender stats writes to `sender_stats` table) and Phase 7 (undo relies on `user_actions` inverse-action-data).

---

## Goals
1. **Flyway V1 schema migration** creates 3 tables with exact column shapes: `user_accounts` (1 row per OAuth login), `sender_stats` (1 row per sender per account), `user_actions` (1 row per bulk-action commit). Includes indexes for the queries Phase 4-7 will run. No DDL writes outside Flyway — `spring.jpa.hibernate.ddl-auto=validate` only.
2. **JPA entity model** for all 3 tables, with Spring Data `JpaRepository<>` interfaces. All date fields use `Instant` (UTC). FK columns backed by `@ManyToOne(fetch=LAZY)` + `@JoinColumn(foreignKey=...)`.
3. **AES-256-GCM encryption utility** (`CryptoUtil`) with env-driven `AES_256_KEY` (32 bytes, base64-encoded). Encrypts refresh tokens + access tokens BEFORE DB write; decrypts on read. Returns `{ciphertext_base64}|{iv_base64}|{tag_base64}` serialized column format or (preferred) single binary `bytea` with random 12-byte IV + GCM tag appended = AEAD blob. Plaintext NEVER logged, NEVER written to actuator endpoints, NEVER returned via API.
4. **Custom `JpaOAuth2AuthorizedClientService`** (implements Spring's `OAuth2AuthorizedClientService`) replaces Phase 2's `InMemoryOAuth2AuthorizedClientService`. Writes: after OAuth callback success → upsert `user_accounts` row with encrypted refresh/access tokens. Reads: when Spring needs token for `@RegisteredOAuth2AuthorizedClient` → loads `UserAccount` + decrypts → builds Spring `OAuth2AuthorizedClient`. Delete: when user signs out → wipe user's rows from all 3 tables (cascading delete).
5. **Sign-out cascade delete** wired into Spring Security's `LogoutSuccessHandler`. After existing session invalidate + cookie delete, call `accountService.deleteByAccount(email, provider)` → DELETE rows in order: `user_actions` → `sender_stats` → `user_accounts`.
6. **Local dev loop** with Docker Compose + Postgres 16 Alpine. `docker-compose up db` exposes port 5432 with a persistent named volume. Flyway disabled in `application.properties` by default; env var `FLYWAY_ENABLED=true` OR CLI flag `--spring.flyway.enabled=true` enables it for real runs.
7. **Test-time schema validation approach:** H2 in PostgreSQL compatibility mode for in-process Flyway schema validate + entity roundtrip unit tests (no Docker required in `mvn test`). Test property source sets `spring.datasource.url=jdbc:h2:mem:tidymail_test;MODE=PostgreSQL;DB_CLOSE_DELAY=-1;DATABASE_TO_LOWER=TRUE`. Ensures CI runs without Docker.

## Decisions Made in This Phase
- **Flyway first, no DDL-auto writes.** `spring.jpa.hibernate.ddl-auto=validate` catches schema drift. Hibernate must NEVER issue CREATE/ALTER statements. Future schema changes = new V2__, V3__ SQL files only. This avoids Pitfall J8 (hibernate.ddl-auto wiping tables at inopportune moments).
- **AES-256-GCM with random 12-byte IV per encryption** (NIST SP 800-38D recommended IV length for GCM). Never reuse IV. Single BYTEA blob format (iv || ciphertext||tag) to avoid schema proliferation of `*_iv`, `*_tag` columns. Trade-off: harder to eyeball raw DB rows (unreadable blob). Benefit: no accidental IV reuse.
- **AES_256_KEY startup hard-fail.** If env var missing → context refresh fails immediately. No "fall back to plaintext" anti-pattern (which would silently reintroduce PITFALLS J1).
- **`ON DELETE CASCADE` on sender_stats.user_account_id and user_actions.user_account_id** at the DB level (not just JPA CascadeType.REMOVE), because JPA cascade-delete can be bypassed via native queries. DB-level cascade guarantees data hygiene even if sign-out code evolves. Trade-off: can't retain user_actions audit log after sign-out — acceptable for MVP (privacy model wipes all user data on sign-out per REQUIREMENTS §RPZ-1).
- **PostgreSQL TEXT[] via `@JdbcTypeCode(SqlTypes.ARRAY)` and JSONB via `@JdbcTypeCode(SqlTypes.JSON)`** (Hibernate 6 built-ins, no extra dependencies like hibernate-types-62 or Vlad Mihalcea's hypersistence utils). Trade-off: H2-pg mode may have subtle JSONB compatibility gaps → mitigate by keeping inverse_action_data schema simple (flat key/value JSON object, no recursive JSON operators in V1 Hibernate queries).
- **H2 `MODE=PostgreSQL` for in-process tests** keeps `mvn test` Docker-free. Accepting that migration parity isn't 100% (PG-specific features like TIMESTAMPTZ, BYTEA become H2 approximations). Mitigation: V-3.5 cross-check with real PG once per phase.
- **Docker Compose for local DB only; Cloudflare deploy uses managed Postgres (Neon/Supabase)** per STATE.md locked decision #6. Compose file is dev-only; production DATABASE_URL points at the managed provider.

## Risks

- **R-3.1: AES key rollover not supported in V1.** If user rotates AES_256_KEY, all existing ciphertexts become unreadable. Mitigation deferred to Phase 6: `aes_key_id` column added in V1 schema (now, during this Phase 3 write), re-encrypt background job added later. Low risk for MVP personal use (user rarely rotates local dev keys).
- **R-3.2: H2 pg-mode incompatibility with specific Hibernate `TEXT[]` / `JSONB` annotations.** Mitigation: if Phase3PersistenceTest fails with "wrong column type" during persist/reload, fall back to explicit `@Column(columnDefinition="TEXT[]")` + custom AttributeConverter<String[],Object[]> converters. Document the workaround in DECISIONS-AND-TRADEOFFS D3.8.
- **R-3.3: Docker not running during Phase 2 smoke tests — user has Colima but not started.** V-3.2 / V-3.3 real Postgres verification step includes explicit `docker compose up -d db` and requires `docker ps` success. If docker daemon is not running, user must run `colima start` first (will be explicitly listed in STATE.md Lessons Learned carry-forward if needed).
- **R-3.4: Custom JpaOAuth2AuthorizedClientService loading logic: what if Spring looks up by principal.name but we stored by email?** OidcUser principal.getName() is the Subject (sub claim) for Google, which is a numeric Google user ID. That's provider_account_id, NOT email. So we need to use principal.getName() = providerAccountId for the lookup. Actually: store both email AND provider_account_id. Lookup in loadAuthorizedClient: `findByProviderAndProviderAccountId(regId, principal.getName())` instead of by email. `saveAuthorizedClient` also uses principal.getName() as provider_account_id. Email used for display only and for (email, provider) unique index (useful for future cross-device). This is a subtle correctness condition — TK-3.5 code comment MUST call out the lookup key decision explicitly to avoid future bugs.
