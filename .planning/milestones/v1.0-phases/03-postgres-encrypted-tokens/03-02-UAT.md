## Notes

1. **Session token store is still JSESSIONID in memory.** We deliberately swapped only OAuth tokens (access/refresh) to Postgres-encrypted in Phase 3. Per PLAN.md §R-3.3, HTTP session persistence (redis / spring-session-jdbc) is Phase 8 (Deployment Prep) concern. This means a JVM restart today *will* log users out (even though their refresh token is preserved in Postgres, they'd just need to click OAuth once more which is single-click without consent screen when scopes match).
2. **AES key rotation is not implemented.** `AES_KEY_ID` column & property exist per TK, but re-encrypt-under-new-key logic (`REKEY` migration / scheduled job) is deferred to Phase 8 / first real key rotation event. The `user_accounts.aes_key_id` column means Phase 8's re-key job can read each row's keyId, decrypt with old key, re-encrypt with new, update column. Infrastructure is in place.
3. **JpaOAuth2AuthorizedClientService.removeAuthorizedClient()** currently deletes the whole user_accounts row (cascading sender_stats and user_actions). In Phase 7 we'll want "token expiry / revoke → just wipe encrypted_*_token columns WITHOUT deleting account" as a separate code path (e.g. re-auth required, but sender stats cached). For Phase 3, "logout = wipe everything" (per requirements "sign out wipes user data") is correct.
