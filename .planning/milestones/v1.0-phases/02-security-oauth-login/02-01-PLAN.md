# Phase 2 — Security Config + Login Page OAuth buttons

**Rationale:** "No app exists until a user can log in. Without login we have no account context and no further phases can connect to Gmail or Outlook APIs."
**Effort:** Medium
**Dependencies:** Phase 1 complete (Spring Boot 3.5.16 scaffold builds, fat JAR runs)
**Critical path:** Must be complete before Phase 3 (Postgres entities) can test sign-out cascade delete; must be complete before Phase 4 (Gmail MailProvider) can use OAuth2AuthorizedClient for tokens.

---

## Goals
1. Spring Security filter chain with: formLogin page `/login` (permitAll), CSRF enabled, static resources `/static/**` permitAll, actuator `/actuator/health` and `/actuator/info` permitAll (health is unauthenticated), any other request authenticated.
2. OAuth2 login support for Google AND Microsoft, configured PROGRAMMATICALLY via a `ClientRegistrationRepository` @Bean that ONLY registers providers whose environment variables (GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET for Google; MICROSOFT_CLIENT_ID, MICROSOFT_CLIENT_SECRET, MICROSOFT_TENANT_ID for Microsoft) are non-empty. This avoids Pitfall J2.
3. Google scopes exactly: `openid`, `email`, `profile`, `https://www.googleapis.com/auth/gmail.modify`. Redirect template: `{baseUrl}/login/oauth2/code/{registrationId}` → resolves to `${APP_BASE_URL}/login/oauth2/code/google`. Per DECISIONS.md §4.
4. Microsoft scopes exactly: `openid`, `email`, `profile`, `offline_access`, `https://graph.microsoft.com/Mail.ReadWrite`. Issuer URI: `https://login.microsoftonline.com/{tenantId}/v2.0` where tenantId is MICROSOFT_TENANT_ID env or "common" if empty. Redirect template same → `${APP_BASE_URL}/login/oauth2/code/microsoft`. Per DECISIONS.md §4.
5. Thymeleaf `/login` page with TWO large provider buttons: "Continue with Google" and "Continue with Microsoft (Outlook)". Each button rendered only if that provider's client-id is configured (model attributes `googleAvailable:boolean`, `microsoftAvailable:boolean`). If BOTH are empty, render a warning banner: "No OAuth providers configured. Please fill in GOOGLE_CLIENT_ID or MICROSOFT_CLIENT_ID in your .env file (see .env.example)."
6. Landing page after OAuth: simple Thymeleaf `/dashboard` that shows "Logged in as {displayName} ({email}) via {provider} • Logout" — no mail functionality yet (Phase 4/5). Logout POST button that redirects to `/login?logout`.
7. Unconfigured providers: provider is NOT registered in ClientRegistrationRepository, so hitting `/oauth2/authorization/{providerId}` returns 404 (or our custom error page) rather than 500. MockMvc test asserts this.
8. Direct access to `/dashboard` when unauthenticated → 302 redirect to `/login`. MockMvc assertion.
9. Successful logout via POST /logout → session invalidated, JSESSIONID cookie cleared, redirect to `/login?logout`. MockMvc assertion.

## Decisions Made in This Phase
- **Programmatic ClientRegistration over property-declared registrations** (D1.3 lock-in). Empty `spring.security.oauth2.client.registration.google.client-id=` in application.properties causes Spring Boot OAuth2ClientProperties validator to throw hard startup failure `Client id of registration 'google' must not be empty`. Programmatic `if (hasText(clientId)) { list.add(buildGoogleRegistration()) }` skips unconfigured providers cleanly; unconfigured `/oauth2/authorization/google` naturally 404s instead of 500.
- **OAuthProviderAvailability @Value-injected component over @ConfigurationProperties** — because real env var names don't match spring.boot.property.camelCase conventions — they're UPPER_SNAKE_CASE like `GOOGLE_CLIENT_ID`. `@ConfigurationProperties(prefix="app.oauth")` expects `app.oauth.google-client-id` property format, which doesn't bind directly to raw OS-level `GOOGLE_CLIENT_ID`. Direct `@Value("${GOOGLE_CLIENT_ID:}")` with empty-string default resolves both spring-dotenv .env keys AND real OS env vars correctly.
- **Thymeleaf server-rendered (per DECISIONS §1) over React.** Inline CSS `<style>` blocks over external CSS files for Phase 2 simplicity — externalize to `static/css/` in Phase 6+ when layouts get richer. Inline CSS avoids needing to wire `/static/**` resource handling testing during smoke runs; both templates self-contain all styling. Trade-off: small amount of CSS duplication between login.html and dashboard.html. Cost is low (~30 lines) and worth the simplicity.
- **CSRF ON for logout POST (per Spring Security 6.x defaults).** MockMvc tests use `SecurityMockMvcRequestPostProcessors.csrf()`. Disabling CSRF globally would make PITFALLS.md §J2 worse by opening stateless API routes to cross-site request forgery; we pay the test-wiring cost now to keep the default-secure posture.
- **Default JSESSIONID + cookie (per Spring Session default) for now** — JDBC-backed session store comes in Phase 3 once Postgres is live. In-memory session = tokens also in memory; lost on restart. Correct behavior for Phase 2 since Phase 3 adds the JPA `UserAccount` entity + encrypted refresh token persistence anyway.
- **OAuth2AuthorizedClientService uses Spring's default Autowired InMemory service for Phase 2** (tokens kept in memory, lost on restart). Phase 3 adds custom JPA-backed `AuthorizedClientService` that persists and encrypts refresh tokens (matches PITFALLS J1 plaintext refresh token mitigation). Phase 2 in-memory is fine for the login-button-tracer slice.

## Risks

- **R-2.1: Redirect URI mismatch.** After Cloudflare deploy, the APP_BASE_URL changes from localhost:8080 to a `https://*.trycloudflare.com` domain. Spring OAuth2 `redirectUri` uses `"{baseUrl}"` which auto-resolves based on request. But Google/Microsoft developer consoles MUST have the exact HTTPS redirect URI whitelisted. Not a Phase 2 blocker (Phase 8 concern). `.env.example` section 13 already has big "CRITICAL REMINDER — OAUTH REDIRECT URIS" block covering this, plus examples for both providers. Mitigation already in place: no further Phase 2 action needed.
- **R-2.2: MockMvc tests that rely on env var absence might pass locally but fail on CI if a developer has GOOGLE_CLIENT_ID set globally in ~/.zshrc.** Mitigation: Use `@TestPropertySource(properties = {"GOOGLE_CLIENT_ID=","GOOGLE_CLIENT_SECRET=","MICROSOFT_CLIENT_ID=","MICROSOFT_CLIENT_SECRET="})` at the CLASS-LEVEL of `SecurityConfigIntegrationTest` to FORCE empty values for the test JVM process, regardless of system env. The `@Value("${FOO:}")` syntax means an explicit empty property overrides any OS env var; this is the Spring Environment property-source precedence contract.
- **R-2.3: OAuth2User attributes differ between providers.** Google returns "email" + "name". Microsoft Graph OIDC id-token might return "preferred_username" or "email" claim inconsistently depending on tenant. Dashboard method must have fallback: order of preference: `(getAttribute("email"), getAttribute("preferred_username"), getAttribute("unique_name"), "unknown")`. Returned in D1.4 carry-forward note from Phase 1. TK-2.3 `dashboard()` method MUST implement this fallback chain, not just a single `getAttribute("email")` call. Code comment in LoginController should reference `D1.4 carry-forward: Phase 1 D1.7 + DECISIONS.md §4 attribute-mapping note` so future code-audits understand why the chain exists.
