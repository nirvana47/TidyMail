## In-Sprint Bug Fixes (found and resolved DURING Phase 2 execution, not deferred)

| ID | Symptom | Root cause | Fix | Ref |
|---|---|---|---|---|
| B6 | **Hard startup failure** when zero OAuth providers configured (default out-of-box experience before user fills .env): `java.lang.IllegalArgumentException: registrations cannot be empty` thrown from `InMemoryClientRegistrationRepository` constructor → propagates as `BeanCreationException` for `clientRegistrationRepository` bean → JVM aborts. | `InMemoryClientRegistrationRepository(List<ClientRegistration>)` constructor in Spring Security 6.x performs a `org.springframework.util.Assert.notEmpty(registrations, "registrations cannot be empty")` check. When both GOOGLE_CLIENT_ID and MICROSOFT_CLIENT_ID are empty (the default .env-less state), our TK-2.2 code correctly skips both ClientRegistration builders → list size = 0 → IAE. This is a catastrophic failure for first-run UX (can't even hit /login to see the warning banner). | Two-part fix in `SecurityConfig.clientRegistrationRepository()` lines 136-152: (a) Guard the `InMemoryClientRegistrationRepository` instantiation with `if (registrations.isEmpty())` check, (b) When empty, return an anonymous-inner-class `ClientRegistrationRepository` stub whose `findByRegistrationId(String)` always returns `null`. Returning null from `findByRegistrationId` is the exact same contract as "this provider isn't registered" — `/oauth2/authorization/google` naturally 404s, OAuth2AuthorizedClientService injection succeeds because the bean is a non-null valid implementation, and the login page falls back to its warning banner. No `@ConditionalOnMissingBean` gymnastics needed. Also conditionally skip `.oauth2Login()` DSL call entirely in `filterChain()` lines 68-75 when zero providers configured — avoids the OAuth2ClientAuthenticationFilter trying to resolve registrations on an empty repo. | SecurityConfig.java:68-75 (conditional oauth2Login wiring) + SecurityConfig.java:136-152 (empty→stub repo fallback) |
| B7 | **DSL configuration error** during initial `filterChain()` draft: Second call to `.authorizeHttpRequests(...)` threw `IllegalStateException: This method cannot be called on the same builder instance more than once` (Spring Security 6.x AuthorizeHttpRequestsConfigurer re-entry guard). | Original draft code structured the DSL as two separate `.authorizeHttpRequests()` blocks: (1) first block handled static/login/actuator permitAll, (2) second separate block handled `/oauth2/**` + anyRequest authenticated. In Spring Security 6.x the `authorizeHttpRequests(Customizer)` call is **write-once per SecurityFilterChain** — calling it a second time invokes a second `AuthorizeHttpRequestsConfigurer` that detects a prior registration and aborts. This is a known 5.x→6.x migration gotcha; 5.x silently merged configurers but 6.x enforces single-use. | Merged ALL matchers into a **single** `.authorizeHttpRequests(auth -> { ... })` closure (SecurityConfig.java lines 43-53). Inside one closure: 4 individual `auth.requestMatchers(...).permitAll()` calls covering static/login, actuator health/info, `/oauth2/authorization/**`, `/login/oauth2/code/**`, followed by one `auth.anyRequest().authenticated()`. Single closure = single configurer. Documented the single-call constraint in code comment lines 38-41 to prevent regression. | SecurityConfig.java:38-53 (merged single authorizeHttpRequests block + comment) |
| B8 | **LoginController always showed warning banner even when env vars were set** — V-2.4 smoke test with GOOGLE_CLIENT_ID=fake-id repeatedly returned warning banner instead of Google button. Debug: `availability.isGoogleConfigured()` returned `false` inside `login()` handler even though the same bean returned `true` when injected into `SecurityConfig.clientRegistrationRepository()`. Contradiction pointed to two different instances of `OAuthProviderAvailability`. | Original TK-2.3 controller signature followed the PLAN.md spec exactly: `public String login(Model model, OAuthProviderAvailability props)`. Declaring `OAuthProviderAvailability` as a Spring MVC **handler method parameter** (not constructor/field injected) triggers `ServletModelAttributeMethodProcessor` which creates a **fresh, new instance via the no-arg constructor** and attempts web-data-binding of request parameters onto it — it does NOT resolve the `@Component` singleton from the Spring context. This fresh copy completely bypasses `AutowiredAnnotationBeanPostProcessor`, so none of the 5 `@Value("${GOOGLE_CLIENT_ID:}")` field injections run — all fields are null/empty string Java defaults. Result: every `isXxxConfigured()` returns false from the MVC-param copy, regardless of real env vars. Discovered by adding a temporary `@GetMapping("/debug-env")` constructor-injected debug endpoint that always returned `true` for `isGoogleConfigured`, while the handler-method-param version always returned `false` — same code path, different bean instance. Root cause is a subtle Spring MVC distinction: **only `@ModelAttribute`-like types get auto-instantiated as handler params**; singleton beans must be injected via constructor or `@Autowired` fields. | Refactored `LoginController` to use **constructor injection** for `OAuthProviderAvailability` (lines 29-33). Added a class-level `private final OAuthProviderAvailability availability` field. Removed `OAuthProviderAvailability props` from both the `login()` method parameter list (line 36) and the `dashboard()` method parameter list. Handler methods now reference `this.availability` singleton. Added explanatory comment lines 21-28 warning future contributors NOT to move this back to a handler method parameter, explicitly naming `ModelAttributeMethodProcessor` + no-arg-constructor instantiation + no `@Value` injection as the failure mode. Verified fix: V-2.4 smoke test now correctly renders Google button (grep count=1) and suppresses Microsoft button (grep count=0). | LoginController.java:21-33 (constructor injection + warning comment) + LoginController.java:36 (method signature without props param) |
