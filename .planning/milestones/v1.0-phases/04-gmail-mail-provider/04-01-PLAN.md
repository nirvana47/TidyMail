## 1. Why this phase exists

Phase 2 gave us login buttons that work for Gmail & Outlook OAuth, and Phase 3 gave us encrypted persistence of the resulting refresh tokens. We now have everything needed to call the Gmail API as the user — but no code that actually does so. **The app cannot yet read a single message.** This phase wires the Gmail SDK against the provider-agnostic `MailProvider` interface that Phase 6 (sender aggregation) and Phase 7 (bulk actions) will depend on. Phase 5 (Outlook) will implement the same interface against Microsoft Graph, so the interface shape MUST be provider-agnostic.

Privacy gate: REQUIREMENTS §GML-1 enforces `format=METADATA` exclusively. This is a hard privacy contract — TidyMail never downloads, decodes, or stores email bodies even on the server side. Phase 4 introduces the METADATA-only integration test that fails if anyone ever changes the format to `full` / `raw` / `minimal`.

## 3. Decisions & trade-offs (locked before execution)

| ID | Decision | Alternatives rejected | Why |
|---|---|---|---|
| D-4.1 | `MailProvider` methods always take a **fully-populated `UserAccount` entity** as first arg (not email / provider-string / accountId-Long) | Alternative: pass `(provider, accountId)` and load inside impl | The JpaOAuth2AuthorizedClientService already loaded the account on OAuth session init; passing the hydrated entity avoids a repository hit and keeps the provider-accountId stable-key logic in one place. |
| D-4.2 | METADATA format enforced at **two levels**: the Gmail API call parameter AND a DTO assertion that `body()` throws. | Single-level guard (API call only) | Someone later refactoring to bypass `GmailMailService` and call `Gmail` directly could still fetch full bodies; DTO-level guard means the typed data that Phase 6/7 code actually sees CANNOT ever contain body bytes, independent of transport bugginess. |
| D-4.3 | `metadataHeaders` whitelist is a `static final Set<String>` in [GmailMailService.java]() — **not** configurable via env | Env / properties configurable list | Would allow accidental widening in production and break the privacy promise. The only "safe" way to change the list is a code change + new test assertion. |
| D-4.4 | Use Google API client's **built-in JSON batch endpoint** (`POST /batch/gmail/v1`) instead of `com.google.api.client.googleapis.batch.Batch` generic class | Alternative A: generic `Batch`; Alternative B: parallel individual requests for each message | Gmail-specific JSON batch is the officially-documented batching surface for modify operations (modifyMessage is a single JSON body with array of ids — up to 1000 ids per call). |
| D-4.5 | `GmailClientFactory` uses **`GoogleCredentials.create(RefreshTokenFlow)`** (google-auth-library-oauth2-http native) with fresh `GoogleCredentials.toBuilder()` per `UserAccount` call; token expiry refreshed automatically inside client transport | Alternative: pre-build `Gmail` service per-account in a caffeine cache | Account-per-user, so cache-hit would be one user; but user may call 20 times/day, so rebuilding is cheap and avoids the pitfalls of cache invalidation when user changes their account password and revokes all refresh tokens. |
| D-4.6 | `BulkActionResult` has `List<String> failedMessageIds` (with reason map) alongside `succeededCount`, `requestedCount`, rather than a hard fail on the first error | Fail-fast: any error throws RuntimeException for the whole batch | Real inboxes have 404 (message deleted between list and batch) for ~1% of ids during normal operation; batch operations must not crash the job. Idempotency guarantee. |

## 5. Known risks & in-sprint bug candidates (PITFALLS.md carryover)

- **Pitfall G1: Gmail OAuth scopes mismatch.** Even if GCP Console says "gmail.modify", the OAuth2ClientRegistration.scope list declared in SecurityConfig §Google must literally contain the string `https://www.googleapis.com/auth/gmail.modify`. If it says the short-form alias `gmail.modify` or `gmail-api`, Google rejects with scope_not_found. Tracer T4(c) will validate the refresh-token credential constructed has all required scopes.
- **Pitfall G2: `userId=me` not `userId=email@email.com`.** Gmail API v1 docs emphasize `me` resolves via the authenticated credential; passing the user's email as userId works for their primary account but breaks for aliases and delegated accounts. Always use literal string `"me"`.
- **Pitfall G3: METADATA format does NOT include the `raw` field and does NOT populate `payload.body.data`.** This is the whole point, but it means naive "iterate parts and collect body text" code from Stack Overflow WILL throw NPE. The `MailMessage` DTO has no body field; tests must fail if it is ever added.
- **Pitfall G4: Google JSON Batch endpoint quotas.** A single JSON batch request with 1000 msg ids counts as 1 quota unit (not 1000), but each `batchModify` call is a "mail read/write" op that counts toward the 250 reqs/sec/project-wide quota. TK-4.5's SYNC_GMAIL_API_BATCH_DELAY_MS default 100 ms means 10 calls per second per user = 25x safety margin below Google's quota.
- **Pitfall G5: Application name `TidyMail/0.1.0`.** Google's `Gmail.Builder.setApplicationName(...)` is NOT cosmetic; it sets the User-Agent header that Google's abuse filters key off. Missing or null → 403 quotaUserBlocked from time to time even for personal accounts. TK-4.3 asserts this string explicitly in the factory.
- **Pitfall J9 carryover: `NoClassDefFoundError com/google/common/util/concurrent/MoreExecutors`** if guava version isn't pinned exactly. Pom.xml already pins guava 33.3.1-jre and uses `<exclusions>` from google-api-client to prevent downgrade. Monitor test classpath.
