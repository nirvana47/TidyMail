## 1. Context & Phase Goal

**Why now.** Phase 4 locked the `MailProvider` interface and compiled Gmail backend. The user can now log in via Google (V-4.7 partial PASS — real OAuth client registration wired) and list METADATA-only inbox pages. What's missing is the first user-visible **value surface**: a paginated row of sender cards the app can recommend bulk cleanup for, and a separate "reply-zero" queue of personal threads you forgot to answer. Phase 6 delivers those purely in backend APIs (JSON DTOs + persisted stats) so Phase 7 can drop Thymeleaf/htmx fragments onto a working data layer without backend churn.

**Input contract (from previous phases, DO NOT ALTER):**
- `MailProvider` interface ([MailProvider.java](file:///Users/bytedance/Documents/trae_projects/TidyMail/src/main/java/com/tidymail/mail/MailProvider.java)) — 5 methods, each takes `UserAccount`.
- `MailMessage` record: `id / threadId / provider / receivedAt / headers`. Helper `getHeaderSingle(name)` with case-insensitive fallback; `from() / to() / subject() / date()` shorthand; **`body()` throws `UnsupportedOperationException` — METADATA-only privacy guard preserved in this phase and downstream callers.**
- `SenderStat` entity already exists in JPA + Flyway V1 DDL. Fields carry `hasListUnsubscribe`, `hasPrecedenceBulk`, `oldestMessageAt`, `newestMessageAt`, `totalCount`, `unreadCount`. Note: entity does NOT yet hold `replyCount` or `bulkMarketingScore` computed fields — those are added in this phase as transient derived columns on the response DTO (see §2 DTO strategy).
- `SenderStatRepository.findByAccountIdOrderByTotalCountDesc` already returns correct count-desc ordering (fixes A2 "sort alphabetically" pitfall).
- Existing Phase 4 helpers available as `public static`: `GmailMailService.extractDomain(rfc5322Address)` (with `"@nodomainprefix"` guard per B18 fix) and `GmailMailService.toMailMessage(...)` format guards.
- Phase 3 persistence tests already cover: UserAccount create → cascade delete → FK references wiped → JPA H2 happy path.

**Deliverable (user story).** As a Gmail-authenticated TidyMail user, I can hit:
1. `GET /api/senders?page=0&size=20&sort=countDesc|oldestFirst|scoreDesc` → 20 sender cards (grouped by from-email with domain-level rollup counts in response envelope). Each card shows count, unread, oldest/newest message timestamps, domain, displayName, a `bulkMarketingScore` 0–3 integer, and `replyCount`.
2. `GET /api/reply-zero?olderThanDays=3` → list of threads the recipient has not yet replied to from personal (non-bulk) senders that are ≥ N days old.

Both endpoints return 401 if unauthenticated. Both paginate with opaque `nextCursor` strings. The sender list additionally persists a snapshot of aggregated SenderStat rows per-account so the Phase 7 UI can render offline from cache between syncs.

### bulkMarketingScore heuristic (0 → 3, higher = more likely bulk/newsletter)

Per ROADMAP §Phase 6, applied inside `SenderAggregator.accumulate()`:

| Point | Condition | Guard (avoid false positives) |
|---|---|---|
| +1 | ANY message from this sender has `List-Unsubscribe` header present (non-blank). Case-insensitive header name match via `MailMessage.getHeaderSingle`. | `List-Unsubscribe` present AND either `value.startsWith("<")` (RFC 8058 URL form) OR contains `mailto:` or `https://` — not a random placeholder string. |
| +1 | ANY message from this sender has `Precedence` header equals `"bulk"` (case-insensitive trim). | Use `equalsIgnoreCase`. Only award if `Precedence` exact single-value equals bulk, not a substring. |
| +1 | `replyCount == 0` AND `oldestMessageAt` is > 7 days before `Instant.now()`. Both required for this point. | Guard skips award if totalCount ≤ 1 (single-message conversation is too early to call "no reply pattern"). |

Range = [0, 3]. A personal thread from a work colleague typically scores 0; a legitimate product marketing newsletter typically scores 2 (List-Unsubscribe + aged + reply=0 → 3); a corporate HR blast with Precedence:bulk but young → 1 or 2.

### ReplyZeroDetector personal-sender heuristic

Mark a thread's from-address as **personal (not bulk)** when:
- `bulkMarketingScore == 0` AND
- Its `fromDomain` is NOT a known bulk-mail domain (built-in small blocklist: `mailchimp.com`, `sendgrid.net`, `amazonses.com`, `mailgun.net`, `constantcontact.com`, `aweber.com`, `convertkit.com`, `hubspotemail.net`, `sendinblue.com`, `getresponse-mail.com`, `postmarkapp.com`, `sparkpostmail.com`, `mailjet.com`, `sendgrid.com`, `yahoo-mail.com` — hardcoded set, case-insensitive match on `fromDomain`. Regex `(.*\.)?(domain)\.com` on each to also catch `e.example.sendgrid.net` subdomains).

Additionally exclude from Reply Zero: any thread where the user's own `account.getEmail()` appears in ANY From header in the thread (recursive via `MailProvider.getThreadMetadata(threadId)`). This filters out threads we've already answered (the whole point of reply-zero).

Guard against spam from random domains even when score=0: require that `fromDomain` matches the second-level domain of AT LEAST one `To` recipient (i.e. sender is in same or known-other SLD as any To person). This avoids "diamond-ring@hotmail.ru phish appearing as 'reply zero personal'". If `To` is a mailing list (empty) → skip the item.

### persist strategy (avoid J6 pitfall)

`SenderStatsPersistService.upsertAccountSenderStats(Long accountId, Map<String, SenderAccumulator>)` does:
```
for (accumulator per fromAddress):
  existing = repo.findByAccountIdAndFromAddress(accountId, fromAddress).orElseGet(new SenderStat());
  copy accumulator.fields into entity;
  repo.save(entity);      // single save() per row — no raw merge() call
```
Annotate method with `@Modifying @Transactional` (State §LL-J6 pattern). In tracers, Hibernate dirty-write checking handles updates correctly without `EntityManager.merge`.

### Cursors (opaque pagination)

For both `/api/senders` and `/api/reply-zero`, encode pagination as:
- **First call:** no cursor → invoke `MailProvider.listMessages(..., null, maxResults)`.
- **Subsequent calls:** pass `pageToken` from previous `PageResult.nextPageToken()`.
- Wrap in base64-url-safe `encode(googleNextPageToken + "|" + offset + "|" + localSort)` so we can re-sort locally while preserving Gmail's original token. Use `java.util.Base64.getUrlEncoder().withoutPadding()` + decode with explicit split on `"|"`. Treat decode failure as "bad cursor" → HTTP 400 with `{"error":"bad_cursor"}`.

### Cross-cutting: unread handling

Gmail METADATA doesn't expose `UNREAD` label through `format=METADATA` + whitelisted headers alone. Unread state comes from Gmail `labelIds` array on the slim `Message` object returned in `users.messages.list()`. Phase 4 currently drops `labelIds` because only `id` + `threadId` are used.

**Fix required in GmailMailService**: include labelIds in each slim `List<Message>` response, then expose to `SenderAggregator` through a new wrapper field on MailMessage. Options:

| Approach | Pros | Cons |
|---|---|---|
| **(A).** Add `labelIds` to `MailMessage` record | Single source of truth | Breaks MailProvider interface lock (MailMessage is part of contract signature in `listMessages(...) : PageResult<MailMessage>` — but interface itself doesn't mention record fields). Actually `MailMessage` is a return value (not a param), so adding a field is source-compatible. Callers that don't reference `labelIds()` still work. **CHOSEN.** |
| (B). Parallel `Map<String, Set<String>> messageLabelIds` in PageResult | Record fields untouched | Adds complexity everywhere; tests rewrite. |

Going with (A). Add a `Set<String> labelIds()` to `MailMessage` with empty default in Gmail implementation. `Phase 4's existing test (T4(c))` should still pass because it doesn't assert field count on MailMessage (only that headers.size ≥ 3 for each item). If it does break, fix the tracer — no class-level contract checks record size.

## 5. Decisions recorded here (D-6.x)

**D-6.1** — `MailMessage.labelIds` field addition. One-way door? **Reversible** (remove field and re-point callers), but Phase 4 tests will need updating. Rating: **two-way / reversible** → no checkpoint.

**D-6.2** — bulkMarketingScore fixed 3-point heuristic (not env-tunable). Rating: reversible via refactor → **two-way**. No checkpoint. Explicitly non-AI (per Scope §locked-decision-2).

**D-6.3** — Reply Zero personal-sender heuristic combo of (score==0) + blocklist + SLD-match To-domain. Rating: **two-way**. Tunable params in future env vars (`REPLY_ZERO_OLDER_THAN_DAYS=3`, `REPLY_ZERO_BULK_BLOCKLIST=a,b,c`). For now hardcoded; no checkpoint.

**D-6.4** — SenderStat upsert: latest-wins (not increment-sum). Why? Represents a re-sync snapshot, not an additive delta. Increment would double-count if the same message appears twice across pages. Rating: **reversible** (change merge strategy in service impl). Two-way → no checkpoint.
