Implementation contract

Build Notes

This page defines which design claims are backed by Gmail APIs and which claims must be conditional. Future implementation should follow these notes before turning UI text into backend logic.

Product model

Individual user

  • Each signed-in user manages only their own authorized email addresses.
  • Use “All my connected emails” for multiple addresses owned by the same user.
  • Do not use family/person labels such as Husband, Wife, or Both accounts.
Progress display

No fake percentages

  • Safe default: “Loaded {indexedCount} messages. Last updated {time}.”
  • Only show total or percent when the backend has a reliable denominator.
  • If a total comes from Gmail estimate fields, label it as approximate.

Gmail Data Contract

UI claim Source Design rule
Signed-in email users.getProfile.emailAddress Safe to show as exact.
Total mailbox messages users.getProfile.messagesTotal Safe as mailbox-wide total, not as a filtered cleanup denominator.
Filtered query total users.messages.list.resultSizeEstimate Estimate only. Use “about” or avoid percent.
Loaded so far Local sync/index records Safe as exact if counted from local persisted rows.
Attachment/storage estimates Message.payload.parts and Message.sizeEstimate Safe as estimates after message metadata is fetched.
Incremental updates historyId and users.history.list Safe after initial sync; fall back to full sync if history is too old.

Analytics Page Contract

  • “Loaded X out of Y” should only be shown if the backend can produce a reliable loaded denominator for the active provider/account. If Gmail and Outlook do not expose equivalent reliable total counts for the chosen scope, keep the current “Loaded X messages” wording instead.
  • Analytics operates on one active account at a time; do not show multi-account counts in the page body.
  • Top filters are shown as two left-aligned buttons only: Time period and Group By. Time period opens a calendar with quick options only after click; Group By opens Day, Week, Month, and Year choices only after click. Do not show either option list inline by default.
  • All analytics sections on the page, including metric tabs, the main graph, Top Received, Top Sent, size cards, and the final actions graph, must respect the selected Time period and Group By filters where applicable.
  • Group By default should be intelligent based on selected time period while allowing user override.
  • Metric tabs are clickable and switch the column chart; column width changes based on time range and grouping.
  • Top Received and Top Sent are compact two-column tables with max 10 rows, not pill cards. The left column is the email address or domain; the right column is the count and is right aligned.
  • Top Received supports flat Email address and Domain tabs with counts. Top Sent supports Email address only with counts.
  • Size cards use total message size, inclusive of attachments, not just individual attachment size.
  • The final graph shows TidyMail Archived vs Deleted counts.

Account & Session Contract

  • MVP initially connects Gmail accounts; Outlook is a future provider.
  • Add new account appears as an option inside the left rail account dropdown.
  • If Add new account is selected, route the user to the provider connection flow.
  • The left rail footer includes a Logout control above Feedback and Collapse rail. The logout menu has two choices: Logout and Delete my data and logout.
  • Logout signs the user out while retaining local logs, indexed data, user data, connected account records, analytics/cache data, and settings for the next login.
  • Delete my data and logout must fully purge stored logs, indexed email metadata, connected account data, queued actions, analytics/cache data, provider tokens, and user settings. The next login starts as a fresh setup.
  • Delete-data logout must require confirmation and must not retain app logs or data tied to the user after completion.

Refresh behavior

The UI may refresh local sync status every 5 seconds. That refresh should read the app’s own sync table or job status, not call Gmail every 5 seconds.

Action safety

Before archive, delete, mark-read, or unsubscribe execution, calculate exact mailbox effects from materialized message IDs in the local index. Do not execute actions from estimated counts.

Conditional UI

Loading banner

  • Show “Mail is still loading” only while an actual sync/index job is active.
  • Hide the banner when loading is complete, no job is running, or the account is idle.
  • Do not replace the hidden banner with placeholder whitespace.
  • If shown, the banner should include a clear link to Analytics where progress details are visible.
Mock removal

No bottom next-step pill

  • The old “Next cleanup step” footer pill was a canvas/navigation mock only.
  • Do not implement it in the product UI.
  • Navigation should happen from the left rail or explicit page actions only.

Review Page Contract

  • Review is a LIFO queued-action ledger: order internally by queued_at and sequence descending.
  • Do not show queued time or queued order to users; keep those fields internal only.
  • Top bulk buttons must show Execute / Undo when nothing is selected, or Execute N / Undo N when rows are selected.
  • Each row action area should use an orange high-attention Undo button plus an ellipsis menu.
  • The row ellipsis menu should include View Emails and Execute.
  • Clicking Execute or Undo must ask for confirmation and show the number of emails affected.
  • If selected actions include Delete, show a separate delete warning: messages will move to Trash and can only be undone/restored during the 30-day trash window.
  • For Archive and Bulk Unsubscribe queued actions, a single standard confirmation warning is enough.
  • View Emails reuses the Bulk Unsubscribe View Stats modal UI for implementation simplicity and consistency, including top action buttons, incoming email distribution chart, and compact email table with columns Sender name, Subject, snippet, and Date received.
  • For Bulk Archive/Delete and Unread Only queued actions, View Emails shows the affected email list.
  • For Bulk Unsubscribe queued actions, View Emails shows past emails from that sender.

Bulk Cleanup Page Contract

  • Do not add a search box to the Bulk Archive/Delete page unless the product later explicitly needs sender search.
  • The email account selector belongs only in the left rail, not inside the page content.
  • Show sender categories as closed dropdowns by default. Each category should show only sender count and optional total size.
  • Use exactly two primary page controls: Settings and Expand all / Collapse all.
  • Settings changes the per-sender action between bulk archive, bulk delete, and mark as read.
  • Expanded categories show sender, email count, optional size, domain, and one action button matching the current Settings action.
  • The action button label should change based on Settings, but its high-attention color should stay consistent across archive, delete, and mark-read.
  • Other is special: senders must be selectable before moving them into an existing category or creating a new category.
  • Move and create category actions should open a centered modal. Do not place the full category-management workflow inline on the page.
  • User-created categories should appear below the closest predefined category and carry a clear “User generated” label.
  • User-created category names must be validated server-side and client-side: trim whitespace, enforce a reasonable length limit, reject control characters, reject HTML/script syntax, escape output, and store/display names as plain text only.
  • Category size is optional. Hide it or mark it as estimated if reliable size totals are not available from indexed Gmail metadata.

Unread Page Contract

  • Unread Only should use the same quiet structure as Bulk Archive/Delete: rail-only account selector, simple header, optional loading banner, Settings, Expand all / Collapse all, and category dropdowns.
  • Do not show a page-level account selector, search box, filter-pill strip, summary-stat strip, or bottom next-step mock on Unread unless the product explicitly adds those later.
  • Unread categories should group messages into human-readable buckets such as lists/automated mail, older than 30 days, direct mail, attachments, and Other.
  • Lists and automated mail depends on backend classification logic. The UI should not imply the category is manually chosen unless the user overrides it.
  • Unread categories are not mutually exclusive: a list/automated sender may also be older than 30 days or have attachments.
  • Direct mail means likely 1:1 senders rather than list/automated senders. If classification looks wrong, the UI must offer a way to mark the sender as a different type.
  • Expanded Direct mail rows should be sorted by sender volume so the biggest unread senders appear first.
  • Other should follow the same pattern as Bulk Archive/Delete Other: selectable senders plus centered modal actions to move selected senders or create a new category.
  • The per-sender action button label should follow Settings, but the high-attention orange/red color should stay consistent across mark-read, archive, and delete.

Unsubscribe Page Contract

  • Typography should stay compact and polished: page titles around 30px on desktop, lighter weights than the first drafts, single-line table rows where possible, and no oversized “elderly UI” scale unless accessibility mode is explicitly added.
  • Bulk unsubscribe is an individual sender workflow, not a grouping workflow. Do not create categories by grouping senders on this page.
  • Unsubscribe should use the same quiet shell as Bulk Archive/Delete and Unread: rail-only account selector, simple header, optional loading banner, and no bottom next-step mocks.
  • Show two top filters: category and time duration. Category values are Unhandled, Unsubscribed, Archived/Deleted, and All. Add Auto-archive later when Gmail rules/filter creation exists.
  • Keep top controls compact as separate pills, not a full-width filter card. Add a right-aligned Settings pill for default action: Archive or Delete only. Do not include mark-as-read here.
  • The time filter should open a compact calendar popover only when clicked. The popover can show one month if it is cleaner, with quick options on the right: Last week, Last month, Last 3 months, Last year, and All. Always show the exact selected date range in the trigger.
  • Show a compact search pill next to the filters for sender name or domain filtering.
  • Unsubscribe capability depends on backend parsing of List-Unsubscribe headers, unsubscribe links, and provider behavior. The UI must not claim success until execution results are known.
  • Each sender row should show sender/domain, number of emails, and Read %. Read % means the share of parsed emails from that sender that were read.
  • The primary sender button should say Unsubscribe when unsubscribe is possible, otherwise Archive or Delete depending on Settings. Never show Archive/Delete as a combined row label. Later, Block may be added when Gmail rule/filter creation exists.
  • Each sender row should include an ellipsis menu with View stats, Archive all, and Delete all. Later options can include creating Gmail filters and adding labels.
  • View stats opens a centered modal with two top-left action buttons: the row’s primary action, then Archive or Delete depending on Settings.
  • The stats modal’s second top-left action should be visually distinct from the primary unsubscribe action, preferably red for Archive/Delete.
  • The stats modal should show a three-month incoming-email bar chart. Hovering a bar should reveal date and email count. X-axis can show week starts rather than every date.
  • The chart bucket size should adapt to data density: daily bars are fine for sparse senders, but high-volume senders may need weekly or otherwise aggregated buckets so the chart stays readable.
  • Below the chart, show a compact single-line table of emails with Sender name as shown in Gmail, Subject, metadata snippet, and Date received. Use truncation/ellipsis rather than wrapping these columns into two lines.
  • The per-sender primary action button should keep the same high-attention orange/red color even when its label changes.
  • All left-rail email account selectors must keep long email addresses inside the rail using max-width, overflow hidden, and ellipsis/truncation behavior.
